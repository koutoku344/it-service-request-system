# ADR-002 Application Structure

## 1. 前提と要件

本システムでは、申請、承認、認証・認可、管理等の業務機能を実装するApplicationの構成およびコンポーネント間の処理方式を決定する必要がある。

本システムの主要な前提および要件は以下の通りである。

- 小規模な学習・検証環境である
- 同時利用者数は最大20名とする
- 通常操作は3秒以内を目標とする
- 申請、承認、認証・認可、管理等の複数の業務機能を提供する
- 業務機能の追加・変更による他機能への影響を可能な限り限定する
- API受付、業務ロジック、Databaseアクセス等の技術的責務を分離する
- コンポーネント間は明確に定義されたInterfaceを介して連携する
- 初期構成では大量の非同期処理や長時間処理を想定しない
- 現在の要件を超える構成要素を追加せず、構成および運用の複雑性を必要最小限とする

これらを踏まえ、以下の2段階でApplication構成を検討する。

1. 業務機能をどの単位でApplicationへ配置するか
2. コンポーネント間の処理を同期・非同期のどちらを基本とするか

## 2. 主な判断基準

本判断では以下を主要な判断基準とする。

- 要件適合性
  - 現在のシステム規模および業務機能に適した構成であること
  - 過剰な構成・機能でなく、要件に適した構成であること

- 責務分離
  - 業務機能および技術的責務を論理的に分離できること

- 変更容易性
  - 機能追加・変更による他機能への影響範囲を可能な限り限定できること

- 構成の単純性
  - Applicationおよび関連する構成要素を必要以上に分割・増加させないこと

- 処理方式
  - 現在の処理量および応答性能要件に適した連携方式であること


## 3. 採用アーキテクチャ

初期構成では、Applicationを単一Containerとして構成し、Application内部を業務機能および技術的責務により論理的に分離する。

また、コンポーネント間の処理は同期処理を基本とし、初期構成ではMessage Queueを採用しない。

```text
Nginx
  |
  v
Application Container
  |
  ├─ 認証・認可
  ├─ 申請
  ├─ 承認
  └─ 管理
  |
  ├─ API受付・入力値Validation
  ├─ 業務ロジック
  └─ Databaseアクセス
  |
  v
PostgreSQL
```

Application内部では、以下の2つの観点で責務を分離する。

- 業務機能単位
  - 認証・認可
  - 申請
  - 承認
  - 管理

- システム機能単位
  - API受付・入力値Validation
  - 業務ロジック
  - Databaseアクセス


各業務機能およびシステム機能をModule単位で分離し、機能追加・変更による影響範囲を可能な限り限定する。


## 4. Application構成の比較

Applicationの機能配置方式について以下を比較する。

| 方式 | メリット | デメリット | 評価 |
|---|---|---|---|
| 単一Application・内部論理分離 | 単一Applicationとして構成を単純に保ちながら、Module単位で業務機能やシステム機能を分離できる | Application全体が同一Process / Containerで動作するため、機能単位の独立Deployや個別Scaleはできない | ◎ |
| 機能単位のContainer分離 | 機能ごとに独立Deploy、個別Scale、障害影響の分離等を行いやすい | Container間Interface、Network、Deploy、監視等の設計・管理対象が増加する | ○ |
| Microservices | Service単位で高い独立性を確保でき、機能ごとのDeployやScaleに対応しやすい | Service間通信、データ整合性、障害制御、監視等の設計が必要となり、現在の小規模構成に対して複雑性が高い | △ |

以上より、現在のシステム規模では機能単位の物理分離による効果が限定的であり、構成を単純に保ちながら責務分離を実現できるため、**単一Application + 内部論理分離を採用する。**


## 5. 処理方式の比較

Applicationおよびコンポーネント間の処理方式について以下を比較する。

| 方式 | メリット | デメリット | 評価 |
|---|---|---|---|
| 同期処理 | 処理フローが単純で、Requestに対する処理結果を即時に返却できる。障害発生箇所や処理結果を追跡しやすい | 呼び出し先の処理完了を待つ必要があり、長時間処理や大量処理では応答時間や可用性への影響を受けやすい | ◎ |
| Message Queueによる非同期処理 | 呼び出し元と処理先を時間的に分離でき、負荷平準化や一時的な障害への耐性を高めやすい | Queue、Consumer、Retry、Dead Letter Queue等の設計・監視・運用が追加で必要となり、処理フローも複雑になる | ○ |

以上より、現在は長時間処理や大量の非同期処理を想定しておらず、通常操作3秒以内の同期処理で要件を満たせるため、**同期処理を基本とし、初期構成ではMessage Queueを採用しない。**


## 6. 採用による影響

### 6.1 メリット

- Applicationを単一Containerとして構成し、構成要素を比較的少なくできる
- 業務機能をModule単位で論理的に分離できる
- API受付、業務ロジック、Databaseアクセス等のシステム機能を分離できる
- 機能追加・変更による影響範囲を限定しやすい
- Container間通信やService間通信等の追加設計を抑制できる
- 同期処理を基本とすることで、処理フローを単純に保つことができる
- Message Queueに伴う追加Resourceおよび運用対象を持たない

### 6.2 デメリット・受容する制約

- Application障害時には複数の業務機能が同時に利用できなくなる
- 業務機能単位で独立してDeployできない
- 業務機能単位で個別にScaleできない
- Applicationの規模が大きくなるとModule間の依存関係が複雑になる可能性がある
- 同期処理では呼び出し先の処理時間や障害の影響を呼び出し元が受ける
- 長時間処理や大量処理が増加した場合、同期処理では性能・可用性要件を満たせなくなる可能性がある

これらは、現在のシステム規模、性能要件および学習・検証環境という前提とのTrade-offとして受容する。


## 7. 再評価条件

以下の条件が発生した場合、本決定を再評価する。

- Applicationの機能数およびCode量が増加し、単一Applicationでの変更影響範囲が大きくなる
- 業務機能ごとに独立したRelease / Deployが必要となる
- 特定の業務機能のみ個別にScaleする必要が生じる
- 業務機能ごとに異なる可用性・性能要件が求められる
- 複数Teamが業務機能を独立して開発・運用する必要が生じる
- 外部API等の応答待ちにより同期処理の応答時間が性能要件を満たせなくなる
- AI処理、通知、Batch等の長時間処理が増加する
- 一時的な大量Requestを平準化する必要が生じる
- 呼び出し先の一時的な障害時にもRequestを保持し、後から処理する必要が生じる

これらの条件が発生した場合は、機能単位のContainer分離、Microservices、Amazon SQS等のMessage Queue、非同期Worker等を候補として再評価する。
