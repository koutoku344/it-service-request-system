## 3. 拡張性

### 3.1 機能修正/拡張

- Web、アプリケーション、データベース、ストレージを論理的に分離し、
  各コンポーネントを独立して変更・追加できる構成とする。
- 申請、承認、通知、自動処理などの業務機能を可能な範囲で分離し、
  将来的な業務機能単位の機能追加や処理方式の変更に対応できること。

### 3.2 インターフェース

- コンポーネント間の連携には、明確に定義されたAPIまたは標準的なプロトコルを使用する。
- 外部システムとの連携はAPIを介して実施し、外部システム固有の処理をアプリケーション全体へ直接組み込まない。
- APIの仕様、入力値、出力値およびエラー形式を文書化する。

### 3.3 環境移行・構成変更

- アプリケーションの実行に必要なランタイム、ライブラリおよび依存関係を構成ファイル等で管理し、同等の実行環境を再現できること。
- コンピューティング基盤等の実行環境の変更によるアプリケーションへの影響を可能な限り限定できること。

### 3.4 データ拡張

- 承認フロー、申請項目および各種マスタは、可能な範囲で設定またはマスタデータにより変更できること。
- 利用者数や処理件数の増加に応じて、将来的にアプリケーション、データベースおよびストレージを
  個別に拡張できること。
- データベースのスキーマ変更は、マイグレーションファイルによりバージョン管理し、
  環境ごとに同一の変更を再現できること。

## 4. 保守性

### 4.1 影響局所化

- Web、アプリケーション、データベース、ストレージ、監視などの役割を分離し、
  障害、保守作業および設定変更の影響範囲を限定できる構成とする。
- コンポーネントごとに起動、停止、再起動、更新およびログ確認を実施できること。

※初期構成では単一サーバを利用するため、サーバ障害時にはシステム全体が停止する。コンポーネント分離はコンテナ単位で実施し、障害の切り分けおよび部分的な再起動が可能な範囲までを対象とする。

### 4.2 構成管理

- AWS環境のインフラ構成はTerraformによりコード管理する。
- アプリケーションおよびミドルウェアの構成はDockerfile、Docker Composeファイルおよび設定ファイルとして管理する。
- ソースコード、Terraformコード、Docker関連ファイルおよび設計書はGitHubでバージョン管理する。
- 本番相当の設定値、認証情報および機密情報は、ソースコードやGitリポジトリへ登録しない。
- 環境ごとの差異は設定値として分離し、コードの直接修正を最小限にする。
- 使用するOS、ミドルウェア、ライブラリおよびTerraform Providerのバージョンを記録する。

### 4.3 変更管理

- インフラおよびアプリケーションの変更は、Gitのブランチおよびコミット単位で管理する。
- 変更前に、変更内容、影響範囲、確認方法および復旧方法を整理する。
- Terraformの変更時は、`terraform fmt`、`terraform validate` および `terraform plan` を実施し、適用内容を事前に確認する。
- データベースのスキーマ変更はマイグレーションファイルで管理し、変更履歴を残す。
- 変更後に問題が発生した場合に、直前の安定したバージョンへ戻せること。

### 4.4 ログ・障害解析

- Web、アプリケーション、データベースおよびOSのログを取得する。
- ログには、日時、処理内容、結果、エラー内容および処理を識別できる情報を記録する。
- パスワード、認証情報、個人情報などの機密情報をログへ出力しない。
- コンポーネントごとにログを識別でき、障害箇所を切り分けられること。
- リクエスト単位で処理を追跡できるよう、将来的にリクエストIDまたは相関IDを付与できること。
- 障害発生時に、ログ、監視情報および変更履歴を用いて原因を調査できること。

### 4.5 監視・ヘルスチェック

- Web、アプリケーション、データベースなどの主要コンポーネントについて、稼働状態を確認できること。
- アプリケーションはヘルスチェック用のエンドポイントを提供する。
- CPU、メモリ、ディスク使用率および各プロセスの稼働状態を監視する。
- 異常を検知した場合に、対象コンポーネントを特定できること。
- Dockerコンテナが異常終了した場合に、再起動状態と原因を確認できること。

### 4.6 作業性

- 定型作業は、可能な範囲でTerraform、Docker Composeまたはスクリプトにより自動化する。

## 5. セキュリティ

### 5.1 認証・認可

- ログイン認証を実装する
- ロールによるアクセス制御（RBAC）を実施する
- 管理者機能は管理者権限のみ利用可能とする

### 5.2 通信

- ~~HTTPS通信を使用する~~
- ~~通信データをTLSにより暗号化する~~

※初期構成は接続元IPを限定した学習用検証環境であり、本番データを取り扱わないため、構成簡素化を優先してHTTPを使用する。
※HTTPSおよびTLSによる通信暗号化は、本番相当環境へ拡張する場合に実施する。

### 5.3 データ保護

- データベースを暗号化する
- パスワードはハッシュ化して保存する
- 秘密情報は環境変数または~~Secrets Manager等~~で管理する

※学習環境では Secrets Manager は利用せず、Docker Composeの環境変数で管理する。

### 5.4 ログ

- ログイン
- 申請
- 承認
- エラー

について監査ログを保存する。

### 5.5 弱性対策

- OS・ミドルウェアへ最新のセキュリティパッチを適用する
- 利用ライブラリの脆弱性を定期的に確認する
- コンテナイメージの脆弱性スキャンを実施する

※AWS ECRのイメージスキャン機能は無料利用可能な範囲で実施する。
※AWS Inspectorによる継続的な脆弱性診断は有料サービスのため、本システムでは対象外とする。


### 5.6 DDoS対策

- AWS Shield Standardによる基本的なDDoS対策を利用する
※Shield StandardはAWS標準機能のため追加料金なし。

- ~~AWS Shield Advancedによる高度なDDoS対策を実施する~~
※Shield Advancedは有料サービスのため、本システムでは導入しない。


### 5.7 アプリケーション保護

- SQLインジェクション対策として、プリペアドステートメント（Prepared Statement）、
ORMを利用し、SQL文へ直接入力値を埋め込まない実装とする

- 入力値のバリデーションを実施し、不正な文字列や想定外の値を受け付けない

- 出力時は必要に応じてエスケープ処理を実施し、クロスサイトスクリプティング（XSS）対策を行う。

- ~~AWS WAFによるWebアプリケーション保護を実施する。~~
※AWS WAFは有料サービスのため、本システムでは導入しない。
